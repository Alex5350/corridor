# Glossary

Terms used across this repo's documentation, in plain English first, precisely second. Identity-migration and program terms come first because the business reader needs them; engineering terms follow. Every term here is actually used somewhere in this repo.

| Term | In plain English | Precisely |
|---|---|---|
| IdAM | Identity and access management: the machinery that answers "who are you" and "what may you touch" for every app an agency runs. This repo is a demo of moving that machinery, not of any one app's features. | The discipline covering authentication (who), authorization (what), and provisioning (accounts). Corridor migrates all three for three synthetic applications: sign-in flows (OIDC/SAML), decisions (XACML), and accounts (SCIM). |
| SSO | Single sign-on: sign in once, use every app. The point of a shared identity provider, and the thing users notice most when it is missing or broken. | Corridor demonstrates it indirectly: all three apps validate tokens from the same provider per TrustMode, so one provider account works everywhere after cutover. |
| Federation | Two organizations (or an app and a login service) agree to trust each other's vouching, so the app believes "this is Dana" without ever seeing a password. | The trust relationship between an identity provider and a relying application, expressed here via SAML 2.0 metadata and OIDC client registrations. |
| IdP / SP | IdP: the service that knows the passwords and vouches for users. SP (service provider): the app being protected. In this repo the "SPs" are the three applications. | Identity provider vs service provider (SAML vocabulary). adfs-sim and okta-sim are IdPs; PermitPortal plays SP with an assertion consumer service at `/saml/acs`. |
| ADFS | Active Directory Federation Services: Microsoft's long-serving on-prem login service. Many agencies standardized on it; it is the "before" picture of this migration. | The legacy IdP, simulated by `src/Corridor.AdfsSim`: SAML 2.0 metadata, an SSO POST endpoint at `/adfs/ls`, and signed assertions carrying `upn` and `role` claims. |
| Okta | A widely used cloud identity service. In this repo it is the "after" picture: the modern provider applications move to. No real Okta tenant is used anywhere. | The target IdP, simulated by `src/Corridor.OktaSim`: real OIDC (code + PKCE), SAML IdP mode, SCIM 2.0, and an XACML PDP, per [ADR 0001](adr/0001-simulate-both-providers-locally.md). |
| Why agencies migrate | On-prem identity ages out: every app carries its own trust plumbing, password rules drift, and adding an app means more bespoke wiring. Moving to a central modern provider is really about operating one front door instead of three garages. | The program rationale: reduce per-app trust configuration, centralize provisioning and authorization, and modernize protocols (SAML 2.0 SOAP-era to OIDC/JWT) without stopping the applications. |
| Cutover | The moment an application stops trusting the old login service and starts trusting the new one. Done badly, it is an outage with a project name. | The per-application transition through TrustModes Adfs -> Dual -> Okta, flipped live from the portal's migration dashboard and recorded in `idn.MigrationApps` plus `idn.AuditEvents` ([ADR 0002](adr/0002-dual-trust-cutover.md)). |
| Dual trust | The safety window during cutover: the application accepts logins from BOTH the old and the new provider, so neither side has to be perfect on day one. | `TrustMode = Dual`: the portal's ACS validates SAML from either IdP and its login page shows a chooser; the SOAP service's validator accepts either token kind for the app. |
| Downtime window | A scheduled period when an application is offline so big changes can be made safely. The explicit promise of this program is that there is none. | Avoided by per-app dual trust and a database-held mode: every flip is a running-system state change with rollback one flip away, not a deploy or an outage. |
| Provisioning | Creating and maintaining accounts in a system. During this migration, accounts must exist in the new provider before users' first modern login, or everyone is locked out at 9am. | SCIM 2.0 on okta-sim (`/scim/v2/Users`): list, create, get, put, and patch (active, groups), writing through to `idn.Users` ([ADR 0006](adr/0006-scim-provisioning-bridge.md)). |
| Trace request | The core record of the legacy SOAP app: a request to trace a firearm-related item (licensee, item description, serial) through a case numbered TRC-######. | `CreateTraceRequest` on the TraceLink service; rows in `trace.TraceCases` with statuses Received, UnderReview, Traced, Closed, Rejected and transition rules enforced inside `trace.usp_UpdateStatus`. |
| Import permit | The core record of the portal app: an application to import a quantity of items for a stated purpose, numbered IP-2026-####. | Rows in `perm.ImportPermits` (LicenseeName, ItemDescription, Quantity, Purpose, Status, SubmittedAt, SubmittedBy), listed and created from the portal's Permits pages. |
| SAML 2.0 assertion | The "letter of introduction" the old login service hands the app: an XML document saying who the user is, signed so it cannot be forged, with an expiry so it cannot be replayed forever. | A signed `<saml:Assertion>` with NameID plus `upn` and `role` claims, `Conditions` (NotBefore with five minute skew, NotOnOrAfter), validated by `SamlTokenValidator` in the legacy service and `SamlValidator` in the portal. |
| OIDC | OpenID Connect: the modern way apps sign people in over the web. The user signs in at the provider, the app receives proof it can verify on its own. | Authorization-code flow against okta-sim's `/authorize` and `/token`, with discovery at `/.well-known/openid-configuration`; the portal is a confidential client, the SPA a public one. |
| PKCE | Proof Key for Code Exchange: a one-time password the browser invents so an eavesdropped login code is useless. Standard for apps that cannot keep a secret, which is all apps living in a browser. | S256 code challenge/verifier, mandatory for the `spa` client and length- and method-checked in `Endpoints/Oidc.cs`; verified with a fixed-time comparison at token exchange ([ADR 0003](adr/0003-oidc-pkce-for-spa.md)). |
| JWT | JSON Web Token: the signed claim card of the modern stack. "This is Dana, she is an Officer, and here is who says so." | RS256 tokens minted by `TokenService` (access 15 min, ID 60 min with nonce, service tokens for client credentials), carrying `sub`, `upn`, `role`, `groups`, `jti`. |
| JWKS | The public key list a provider publishes so apps can verify token signatures themselves. Keys are listed by id (`kid`) and can rotate. | `GET/POST /jwks` on okta-sim publishing the current kid `okta-sim-2026-08` plus a retired kid so relying parties exercise rotation; cached by the legacy service via `CachedJwksProvider`. |
| SCIM 2.0 | A standard API for managing accounts across systems, so "create this user" means the same thing to every provider. | RFC 7644 shapes with `application/scim+json` on `/scim/v2/Users`, filter `userName eq "value"`, replace-op PATCH on active and groups. |
| XACML / PDP | A rules language for "who may do what to which thing", plus the service (the policy decision point) that answers those questions. Rules live in readable files, not buried in apps. | `POST /pdp/decide` evaluates role + resource + action triples against `policies/*.xacml.xml` (permit reads for Officer/Admin, permit writes for Inspector, deny-all fallback), first-applicable, default deny ([ADR 0007](adr/0007-xacml-central-pdp.md)). |
| SOAP / WSDL | The XML protocol of the legacy estate, and the contract document that describes it. Old, formal, and still carrying real work everywhere. | SOAP 1.1 over BasicHttpBinding via CoreWCF at `/TraceLink.svc`, WSDL at `?wsdl`, namespace `http://corridor.example/tracelink/2026/08`. |
| WS-Security | The standard for carrying security material inside SOAP messages. This repo uses a deliberately simplified version of its shape. | A `cor:Security` header (namespace `http://corridor.example/security`) holding either a `saml:Assertion` or a `jwt` element, enforced by `CorridorSecurityMessageInspector`; production would use full WS-Trust ([ADR 0004](adr/0004-token-header-for-soap.md)). |
| ADO.NET | The original, explicit way .NET code talks to SQL Server: hand-written calls, no magic, venerable. Preserved untouched here on purpose. | `SqlConnection`/`SqlCommand`/`SqlDataReader` in `TraceCaseRepository`, calling only stored procedures; no ORM anywhere in the legacy service ([ADR 0005](adr/0005-keep-raw-adonet.md)). |
| T-SQL stored procedure | A named program living inside SQL Server. Business rules placed there apply no matter which app calls them, which is why agencies like them for audited rules. | `trace.usp_SearchCases`, `usp_GetCase`, `usp_CreateTraceRequest`, `usp_UpdateStatus` in `db/sql/002_trace_procs.sql`; the last one raises error state 40001 on illegal status transitions. |
| TrustMode | The dial this whole repo turns. Each application's current answer to "whose tokens do I accept?": Adfs, Dual (both), or Okta. | A column on `idn.MigrationApps`, cycled Adfs -> Dual -> Okta (and Okta -> Adfs to roll back) by `TrustModeService`, audited per flip. |
